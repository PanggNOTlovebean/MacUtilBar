# 1.0.1 (2) 候选验证记录

日期：2026-11-15。**尚未完成正式验收，不替代 1.0.0 预发布的限制说明。**

本轮修正了证据采集和降级行为：

- 状态项识别要求同一 CG window ID 的宽度增加 11pt 后恢复，且结果唯一；同时变化的两个窗口拒绝匹配。原先只观察一次增宽，可能碰巧误认别的窗口。
- 实测发现新创建项可能先使用内容固有宽度：HiddenSpacer 初始为 0，探针初始为 34，恢复明确 length 后才稳定到 24/40。识别失败后只重试一次，不能跳过恢复验证。
- 无有效 CG 窗口证据时，不采用 NSWindow 的占位 frame；配置页显示未知数量“—”，诊断 JSON 显式记录 available:false，不再把零矩形当作证据。
- 设置提供系统菜单栏设置入口；系统开关只由用户操作。位置校准期间暂停折叠，避免用户操作与长度恢复竞争。
- autosaveName 延后到主队列下一轮设置，避免在系统挂接状态项之前恢复排序。

## 执行结果

- `swift test`：12 项测试通过，新增恢复宽度、稳定身份和歧义拒绝覆盖。
- `./Scripts/build.sh build/next-candidate`：通用 arm64/x86_64 App + PKG，通过。
- `codesign --verify --deep --strict build/next-candidate/MacUtilBar.app`：通过。
- 通过 Finder 定位并打开 `.app`，设置页明确显示“尚未确认菜单栏图标位置”；正常启动路径仍未通过。
- 只读检查 System Settings → 菜单栏，MacUtilBar 的“允许在菜单栏显示”开关为 on。没有更改任何系统开关，没有重启 Control Center，没有修改受保护偏好。
- 受保护的 Control Center 偏好文件读取返回 Operation not permitted；未尝试绕过该限制。
- `.app --diagnose` 仍没有有效主图标/测试图标窗口证据，因此保持未通过状态。

## 调研依据与边界

[Apple 的菜单栏设置说明](https://support.apple.com/en-asia/guide/mac-help/mchlad96d366/mac)说明显示内容由系统设置控制。[Stats 的开发者问题记录](https://github.com/exelban/stats/issues/3120)报告过相同 `(0,-22)` 占位现象，部分报告与显示许可有关；其中也存在未被维护者认同的解释。因此这些资料只用于决定排查方向，不能直接证明本机根因，也不能据此更改 Bundle ID 或重置系统状态。

下一项需要验证：由用户在正常桌面启动，或在明确授权后只切换 MacUtilBar 自身的系统菜单栏显示开关并恢复原状态。其他应用、全局偏好和 TCC 不在操作范围。VM 的可靠输入问题及其完整验证仍未解决。

## 最终独立程序回归

[真实窗口采样](1.0.1/standalone-frames.json)确认：主图标保持 x=1229，测试图标按全部展开→收起→普通展开→全部展开依次为 x=1127、-2231、-569、1127。最终通用二进制的这条路径通过，但不能替代 `.app` 和安装器验收。

排查发现一个系统音视频指示器原位于 x=883，折叠后改为 x=1181 保持可见，其他五个目标已经移出屏幕。因此将“隐藏机制是否生效”和“是否所有候选窗口均隐藏”分开记录：没有任何目标隐藏或主控制项消失，连续两次才判定整体不可用；部分窗口留下时显示剩余数量，不声称全部隐藏成功，不尝试强行隐藏系统指示器。新增测试覆盖这一区别。系统控制项本来就不属于本产品管理目标。

本轮仍需用户明确授权才能测试系统设置中仅 MacUtilBar 自身的开关关闭/恢复。授权尚未获得，未执行该操作。
